OPTIMIZE THE CMAC MULTIPLIER WITH A STRUCTURAL WALLACE TREE

The Problem

The CMAC multiplier currently uses generic NV_DW02_tree modules for carry-save addition (CSA) tree reduction. These are behavioral models that can be synthesis tool-dependent. Replace them with an explicit structural Wallace tree implementation for better performance and synthesis predictability.

What is a Wallace Tree

A Wallace tree is an efficient circuit for adding multiple numbers in parallel using carry-save arithmetic. Unlike sequential addition where you add numbers one by one with ripple carries, a Wallace tree reduces many inputs down to just two values (sum and carry) in logarithmic depth by using small adder stages in parallel.

The key principle: at each stage, you take groups of inputs and compress them down to fewer outputs using carry-save adders, then repeat until you're down to just two final values. This parallel reduction is much faster than sequential addition because all bit positions can work simultaneously without waiting for carries to propagate.

Your Task

Replace the NV_DW02_tree instances in the CMAC multiplier with structural Wallace tree implementations. 

Study the NVDLA source code to understand:
  - How many NV_DW02_tree instances exist and what they do
  - How many inputs each tree reduces (5 inputs? 4 inputs? other?)
  - What the input and output interfaces are
  - How the data flows through the multiplier
  - How the three operating modes (INT8, INT16, FP16) work

Then design and implement your Wallace tree modules to replace them.

Requirements

Your implementation must:
  - Produce functionally equivalent outputs to the original NV_DW02_tree
  - Support all three operating modes (INT8, INT16, FP16) 
  - Use structural instantiations (no behavioral loops)
  - Maintain the same module interface (no new ports on the multiplier)
  - Be a drop-in replacement (same inputs, same outputs)

File Organization

Place your Wallace tree implementation files in the sources/vmod/nvdla/cmac/ directory (same location as the multiplier you're modifying). This follows NVDLA's organization principle where application-specific modules stay with their parent components, while vmod/vlibs/ is reserved for generic, parameterized library components.

Create as many separate module files as you need for your implementation. Your modules should match the interface of what they're replacing.

Required Component Interfaces

For verification purposes, implement these CSA building blocks with exact module names:

1. 3-to-2 CSA Compressor (REQUIRED):
   Module name: NV_NVDLA_CMAC_CORE_csa32
   Parameters: WIDTH (typically 24 or 32 bits)
   Inputs: in0[WIDTH-1:0], in1[WIDTH-1:0], in2[WIDTH-1:0]
   Outputs: sum[WIDTH-1:0], carry[WIDTH-1:0]
   Function: Reduces 3 inputs to 2 outputs in carry-save format
             (sum + carry equals in0 + in1 + in2)

2. 4-to-2 CSA Compressor (OPTIONAL but recommended):
   Module name: NV_NVDLA_CMAC_CORE_csa42
   Parameters: WIDTH
   Inputs: in0, in1, in2, in3, cin (carry from previous stage)
   Outputs: sum, carry, cout (independent carry chain)
   Function: Dual full-adder cascade (more efficient than 3:2)

3. Wallace Tree Modules (flexible naming):
   Suggested pattern: NV_NVDLA_CMAC_CORE_wallace_*
   Examples: wallace_5to2.v, wallace_4to2.v, wallace_5inp.v
   Requirements: Instantiate your CSA building blocks to create the reduction tree
